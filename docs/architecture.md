# Architecture

AgriSence's frontend is a React single page application, installable as a PWA. The backend
(a separate repository) is the only authority for roles, prices, forecasts, stock and totals.

## Data flow

```
Screen (src/screens/...)
  -> TanStack Query hook (useQuery / useMutation, keys never contain the token)
    -> endpoint function (src/api/endpoints/<area>.js)
      -> api client (src/api/client.js, openapi-fetch + middleware)
        -> backend  VITE_API_BASE_URL + /api/v1/...
```

- Screens never call `fetch`. A source check test fails if `fetch(` or `XMLHttpRequest` appears outside `src/api/`.
- Endpoint functions use the literal paths from `docs/backend/openapi.json` (for example `'/api/v1/health'`),
  return the parsed body and throw `ApiError` on failure. `npm run check:contract` verifies every path and method.
- Types come from `src/api/schema.d.ts` (generated by `npm run gen:types`) and are referenced through JSDoc.
- The single `QueryClient` lives in `src/lib/queryClient.js` (no retries by default, no refetch on focus).
- Price and forecast hooks live in `src/api/queries/` (F2a): `staleTime` 5 minutes, no retry on a 4xx,
  at most two retries with exponential back off on network errors, timeouts and 5xx. `getForecast()`
  returns `{ status: 'ok', data }` or, for 404 `forecast_unavailable` only, `{ status: 'unavailable', reason }`.
  Display rules for these screens: [forecast-display.md](forecast-display.md).
- Listing and order hooks (F2b) live in `src/api/queries/listings.js`: infinite queries with offset
  pages of 20 (30 second stale time, the orders refetch on window focus) and mutations that are never
  retried (`writePolicy`). A successful write invalidates the listing and order keys, which include
  the dashboard counts. Multipart bodies are built in `src/api/endpoints/listings.js` only. Details:
  [listings-orders.md](listings-orders.md).
- Buyer hooks (F3) live in `src/api/queries/buyer.js`: infinite queries for browse and My orders,
  `useOrder` (polls every 3 seconds for up to 150 seconds while a payment prompt is open, paused
  while the tab is hidden, and exposes the server clock offset), and order, pay and cancel
  mutations that are never retried. The navigation badge's count hook is in `waitingCount.js` so
  the shell does not load the other buyer hooks. Only `endpoints/payments.js` sets the
  `Idempotency-Key` header. Details: [buyer-checkout.md](buyer-checkout.md).
- Screen selections (crop, market, horizon, range) are kept in the URL query string and validated.
  `usePageTitle` moves focus to the heading when the pathname changes, not when only the query string does.

### Base URL and prefix

The paths in `openapi.json` already include `/api/v1`. The client base URL is therefore the API
origin only: `VITE_API_BASE_URL=http://localhost:8000` gives `http://localhost:8000/api/v1/health`.
`src/lib/env.js` rejects a base URL ending in `/api/v1` or a slash, and requires https except for
localhost and 127.0.0.1. On failure `src/main.jsx` renders a full page configuration error.

## Client middleware (`src/api/client.js`)

Order of `onRequest`: error handling, timeout, authorization (responses and errors run in reverse).

1. **Authorization:** adds `Authorization: Bearer <token>` when the session has a real token.
   Anonymous calls, development fake sessions and the public auth routes (`PUBLIC_AUTH_PATHS`) send no header.
2. **Timeout:** an `AbortController` per request, 20 s by default, 60 s for multipart uploads, or a per
   call `timeoutMs` (`api.POST(path, { body, timeoutMs: 60_000 })`). A caller's own abort is respected.
3. **Errors:** every non 2xx response throws an `ApiError` (`status`, `code`, `message`, `reason`,
   `requestId` from the body or `X-Request-ID`, `retryAfter` from `Retry-After`, plus `fields`/`details`).
   Network failures become `network_error`, timeouts `timeout` (status 0). Bodies are never logged.
4. **401** from any route except the public auth routes (login, register, accept invite, invite request
   code, password reset request and confirm): clear the session with reason `expired`, navigate to `/login`.
5. **403 `password_change_required`:** mark the session and navigate to `/change-password`.

Navigation from the client goes through `setNavigator()`, wired to the router in `RootLayout` (`src/routes.jsx`).

## Session and guards

```
POST /auth/login -> session.setFromLogin(tokenResponse) -> sessionStorage["agrisence.session"]
                                    |
                     timer at expiresAt, re-check on visibilitychange -> session.clear('expired')
                                    |
     useSession() (useSyncExternalStore) -> RequireAuth / RequireRole / PublicOnly -> screens
```

- `src/auth/session.js` holds `{accessToken, role, mustChangePassword, isSuperAdmin, expiresAt, name}`.
  It persists in `sessionStorage` (this tab only), never `localStorage`, a URL, a log line or a query key.
  An expired stored session is discarded on load. `clear()` also clears the TanStack Query cache.
- `GET /auth/me` (`UserOut`) does **not** return `is_super_admin`. `setProfile()` reads it only if the
  backend adds it, so it stays false today (listed as a backend gap in the README). `setProfile()` also
  refreshes the name, the role and `mustChangePassword`.
- **Flash messages:** `clear(reason)` leaves a one time, in memory message for the login screen
  (`expired`, `password_changed`, `unauthorized`; a sign out leaves a silent one); `setFlash()` sets one
  without a session. The login screen consumes it.
- **Startup revalidation** (`src/auth/revalidate.js`): a session restored from `sessionStorage` is checked
  once with `GET /auth/me` before `RequireAuth` renders anything protected (loading state, at most 8
  seconds). A 401 clears it with `expired`; a network failure keeps it and the offline banner says the API
  could not be reached (`src/lib/connectivity.js`).
- Sign in and the post login redirect: see [auth.md](auth.md).
- Guards (`src/auth/guards.jsx`):
  - `RequireAuth`: anonymous users go to `/login` with the intended path in router state (never in the URL).
    A session with `mustChangePassword` can only reach `/change-password` (which offers logout).
  - `RequireRole`: the wrong role sees the `Forbidden` screen in place, so there is no redirect loop.
  - `PublicOnly` (`/login`, `/register`, `/forgot-password`): a signed in user goes to their role home,
    except while a screen is signing someone in (`useSignInHold`). `/reset-password` and `/accept-invite`
    open with or without a session and show `SignedInNotice` when signed in.
  - Guards only shape the UI. The server checks the role on every request.
- Role areas (`/farmer/*`, `/buyer/*`, `/admin/*`) are lazily loaded with `React.lazy` and `Suspense`
  so one role never downloads another role's screens.
- `src/dev/DevRoleSwitcher.jsx` (development only) creates an in memory fake session (`isDevFake`, no token,
  never persisted) to preview the shells. It is excluded from production builds; `check:build` verifies it.

## Error handling

| Where                              | What happens                                                                                             |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------- |
| API call fails                     | `ApiError` thrown; screens show `ErrorState` with `getUserMessage(error)` and "Reference: <request id>". |
| Unknown error code                 | Generic message plus the reference.                                                                      |
| Render error in a route            | `RouteErrorBoundary` inside the shell shows `ErrorState`; navigating away resets it.                     |
| Failed lazy chunk or routing error | Router `errorElement` (`RouteErrorElement`) with a reload action.                                        |
| Anything else                      | App level `ErrorBoundary` with a reload action.                                                          |
| Invalid environment                | `ConfigErrorScreen` instead of the app.                                                                  |
| Offline                            | `OfflineBanner`: "You are offline. Prices, forecasts and payments need a connection."                    |

`getUserMessage` maps every code in the backend's message table (`src/api/errors.js`); a test parses
`docs/backend/frontend_contract.md` and fails if a documented code has no message.

## PWA caching rules

- `vite-plugin-pwa` with `generateSW` and `registerType: "prompt"`. The service worker precaches only the
  build's static files (JS, CSS, HTML, icons, manifest) and serves `index.html` as the navigation fallback.
- **There are no runtime caching routes.** API responses (prices, forecasts, listings, orders, account data)
  and remote images are never cached by the service worker or anywhere else. A stale price or forecast could
  mislead a farmer's selling decision, and cached account data on a shared phone is a privacy risk.
- Offline use is limited to the app shell and the offline message.
- The worker is registered only in production builds (`PwaUpdatePrompt`, loaded when `import.meta.env.PROD`).
  When an update is waiting, a toast says "A new version is available." with a Refresh action.
- `npm run check:build` fails if the generated worker registers any route other than the navigation fallback,
  contains a caching strategy, mentions `/api/v1` or contains the API base URL.
